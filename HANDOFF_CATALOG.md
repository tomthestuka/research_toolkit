# Handoff — Data-catalog management in download/reduction modules

> **Audience: a build-time coding session working in `research_toolkit`.** This note is
> self-contained; it assumes no knowledge of the sibling `auto_research` orchestration repo.
> It records (a) what already exists, (b) the catalog contract, and (c) the reliability work
> still to build into the download/reduction modules.
>
> These catalog writers are **reliability-bearing** and are built **by hand** (human +
> build-time agent), *not* generated by the runtime tool-author. Build them carefully and
> test them.

---

## 1. Background — what the catalog is and who reads it

Each mission keeps its observations under an `obs_db_path` (one directory per mission). A
**per-mission data catalog** — a single JSON file `<obs_db_path>/catalog.json` — is the
authoritative inventory of *what data is local and how it was produced*. It is the data-side
provenance record: which ObsIDs are present, to what processing level, and for every produced
product the parameters needed to reproduce it.

The **consumer** is the orchestration repo `auto_research` (separate package, sits beside this
one, read-only over the toolkit). It reads `catalog.json` to answer "what is already local?"
so an analyst requests a *download/acquire* only when data is genuinely missing, and to carry
provenance. `auto_research` **only reads** the catalog; it never writes it. **The writers are
the toolkit's own download/reduction tools — this repo.** That write side is what this handoff
is about.

Crucially: this repo **must not import `auto_research`** (hard trust boundary). The catalog
writers are self-contained: plain JSON read-modify-write under `obs_db_path`, no cross-repo
dependency. The JSON *shape* below is the entire contract.

The current mission `obs_db_path`s (from the orchestration config; given here only so you can
locate the live catalogs):

|---|---|

| NICER  | `/data/fzhou/XSPEC/Cyg_X-1/NICER`  |

## 2. The catalog contract (the JSON shape)

```jsonc
{
  "mission": "ixpe",                          // optional; reader defaults it from the path
  "entries": {
    "<obsid>": {
      "obsid": "<obsid>",
      "max_level": 3,                         // highest processing level present: 1 | 2 | 3
      "levels_present": [1, 2, 3],
      "products": [
        {
          "kind": "pcube",                    // e.g. level2_evt | pha | pcube | arf | rmf | ...
          "path": "<path RELATIVE to obs_db_path>",
          "params": { /* parameters used to obtain a level-3 product */ },
          "produced_by": "<tool / script / commit>",
          "created_at": "<iso8601>",          // optional
          "sha256": "<optional>"              // optional integrity hash
        }
      ]
    }
  }
}
```

Rules:

- **`path` is relative to `obs_db_path`** (e.g. `01002901/event_l2/ixpe01002901_det1_evt2_v01_rej_src_pcube.fits`).
- **Level semantics:** HEASARC/archive download supplies up to **level 2** (calibrated/cleaned
  events). **Level-3** products (pcube, PHA, ARF/RMF, …) are produced by reduction and **must**
  record under `params` the parameters used to obtain them, so they are reproducible.
- **Provenance is not fabrication.** Only record a product **after** it is actually on disk.
  Never invent an entry for data you did not produce. A reduction that fails records nothing and
  fails loudly.

## 4. What to build — catalog writers in download/reduction

Add catalog recording at the point each module **produces** data, so the catalog stays a true
mirror of disk. Build a **shared, self-contained catalog helper** and have every producer call
it.

### 4.0 Write-access policy — one trusted writer, no hand-rolling (read this first)

The catalog is a **reliability-bearing provenance record**, so its write path is **prisoned** to
a single trusted code path. This is a hard rule, not a style preference:

- **Exactly one module may mutate `catalog.json`** — the single shared, hand-built, tested
  catalog-writer helper of §4.1. Every producer that lands data on disk records it by **calling
  that one helper**; nothing else opens the file for writing.
- **No hand-rolled catalog writes, ever, by anyone or anything.** Not a producer doing its own
  `json.dump`, not a one-off maintenance snippet, and — critically — **not a runtime
  tool-authored tool.** A runtime-authored tool may *call* the helper, but must never emit its
  own JSON read-modify-write of the catalog. A torn or schema-divergent write breaks every
  reader (the reader hard-errors on malformed JSON, §3.2), which is exactly why the write path
  is centralized and tested instead of re-expressed per producer. The *only* way to write the
  catalog is the way that is correct by construction.
- **Who may change the catalog — the complete list:**
  1. The **trusted data-manipulating tools** — the `heasarc_utils` download/acquire path and the
     wired reduction scripts (`*_red.sh`, `*_grp.sh`, `filter_inst_bkg_IXPE.sh`,
     `lib/red_ixpe.py`) — and **only through the shared helper**, never with their own JSON I/O.
  2. A **human operator acting deliberately (sudo)** — for bootstrap, repair, or
     reconciliation.
  No other actor has a write path: no LLM, no librarian, no ad-hoc script, no runtime author.
- The healthcheck/repair surface that detects and fixes drift is itself part of the trusted
  writer (it is the only thing entitled to rewrite entries) — see §4.1.

### 4.1 Shared helper (suggested `lib/catalog.py`, dependency-free)

A small module with no science-stack or `auto_research` dependency. Suggested surface:

- `read(obs_db_path) -> dict` — load `catalog.json` (or `{"mission":…, "entries":{}}` if absent).
- `upsert_product(obs_db_path, mission, obsid, *, level, product)` — atomic read-modify-write:
  load, ensure the ObsID entry, **upsert** the product (match on `(kind, path)` so re-running
  reduction updates in place and never duplicates), recompute `levels_present`/`max_level`,
  write back atomically.
- Optional `record_event_level(obs_db_path, mission, obsid, level, product)` for the
  download/level-1/level-2 case.

**Reliability requirements** (this is why it is hand-built, not auto-authored):

- **Atomic writes** — write to a temp file in the same dir and `os.replace()` onto
  `catalog.json`. A reader must never observe a half-written file (the reader raises on malformed
  JSON, so a torn write would break downstream runs).
- **Concurrency-safe** — reduction loops process many ObsIDs (NICER: 105) and may run in
  parallel. Serialize read-modify-write with an OS file lock (`fcntl.flock`) on a sidecar lock
  file so concurrent producers don't clobber each other.
- **Idempotent** — re-reducing an ObsID updates the same product entry; never appends duplicates.
- **Truthful** — record a product only after confirming the file exists on disk
  (`os.path.exists`). Optionally compute `sha256`. A failed reduction records nothing.

### 4.2 Wire each producer

| Producer | Module | Records |
|---|---|---|
| **HEASARC download / acquire** | currently **absent** here (`download_IXPE.sh` lives in the data dir; the proper home is a new `heasarc_utils` package) | level-1/level-2 events (`level2_evt`, `produced_by:"heasarc"`) per downloaded ObsID |
| **IXPE instrumental-bkg filter + bin** | `IXPE/filter_inst_bkg_IXPE.sh` (+ `lib/red_ixpe.py:pcube`/`pha`) | level-3 `pcube` / `pha` with `filter`, `detectors`, `calibration_version`, energy binning / region radii |
| **NICER reduction** | `NICER/nicer_red.sh` (nicerl3-spect) | level-3 `pha`/`pha_bkg`/`arf`/`rmf` with `background_model`, `mpu` |
| **NuSTAR reduction** | `NuSTAR/nustar_red.sh` | level-2 cleaned events + level-3 `pha_src`/`arf`/`rmf` per FPM |
| **NuSTAR grouping** | `NuSTAR/nustar_grp.sh` | level-3 `pha_grp` per FPM with `grouping` |

Notes on wiring mechanics:

- **Python producers** (`lib/red_ixpe.py:pcube`, `pha`) can call the helper directly at the end,
  recording the real `ebinning`/`src_rad`/`bkg_inner_rad`/`bkg_outer_rad`/`ra`/`dec`/`irf_date`
  it used into `params` — those args are exactly the level-3 reproducibility parameters.
- **Shell producers** (`*_red.sh`, `*_grp.sh`, `filter_inst_bkg_IXPE.sh`) can't do safe JSON
  read-modify-write in bash — have each loop iteration shell out to a tiny Python catalog CLI
  (e.g. `python3 -m xspec_utils.lib.catalog upsert --obs-db … --mission … --obsid … --kind … --path … --produced-by … --param k=v …`)
  after the product is written. Keep the bash thin; the reliability lives in the Python helper.

## 5. Tests

These modules are reliability-bearing — test them:

- Helper round-trips: write → read returns the same products; `max_level`/`levels_present`
  recomputed correctly.
- **Idempotency:** upserting the same `(kind, path)` twice yields one entry, updated.
- **Atomicity:** an interrupted/torn write never leaves a malformed `catalog.json` (reader must
  still parse).
- **Concurrency:** two writers racing on the same catalog don't lose entries (lock works).
- **Truthfulness:** a product whose file is absent is not recorded (or raises).
- A reduction run on a sample ObsID produces the expected catalog entry with the real `params`.

---

## 6. Constraints (recap)

- **No `auto_research` import** anywhere in this repo. The catalog is plain JSON under
  `obs_db_path`; the shape in §2 is the whole contract.
- **Prisoned write path** (§4.0) — `catalog.json` is mutated **only** through the single shared
  catalog-writer helper, called by the trusted data-manipulating tools, or by a human operator
  (sudo) for repair. **No hand-rolled writes — by any script, agent, or runtime-authored tool,
  at any time.**
- **No fabrication** — record only real, on-disk products; fail loudly otherwise.
- **Keep consistent with the live bootstrapped catalogs** (§3 conventions) so existing entries
  and new tool-written entries interoperate.
